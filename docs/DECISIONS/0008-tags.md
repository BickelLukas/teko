# ADR-0008: Tags as first-class normalized entities

**Date:** 2026-05-30  
**Status:** Accepted

## Context

Real use of the Someday list and the Tasks view surfaced a need for grouping. Households accumulate tasks across rooms, projects, and people. Without a grouping mechanism, the only filters are assignee and recurrence — neither of which maps well to "bathroom tasks" or "urgent this week."

Several approaches were on the table.

## Decision

Tags are first-class entities with a `name` and a `color`, stored in a `tags` table with a `task_tags` junction. They are:

- **Household-shared.** One tag library, visible to everyone. No per-user tag sets.
- **Curated in Settings.** Tags can only be created in Settings → Tags, not inline in task forms. The intentional friction keeps the library small and meaningful.
- **Normalized.** Renaming or recoloring a tag propagates everywhere without any data migration — every join picks up the current state.
- **Uniform across views.** The same chip component renders in Today, Tasks, and Someday.

**Schema:**
- `tags(id PK AUTOINCREMENT, name, color, created_at, created_by)` with a `CREATE UNIQUE INDEX ON tags (LOWER(name))` for case-insensitive uniqueness.
- `task_tags(task_id, tag_id, created_at)` with a composite primary key and cascade deletes in both directions.

**Color palette:** 10 stable keys stored in `shared/src/palette.ts`. The `color` column stores the key, not a hex value, so palette refinements propagate without data migration.

**Filtering:** AND semantics — selecting multiple tags narrows the result. This matches how households actually think ("show me basement AND urgent tasks").

**Tag assignment:** `POST /api/tasks/:id/tags` with replace semantics. A single call sets the full tag set; no individual add/remove endpoints. Keeps the surface small.

## Consequences

**Positive:**
- Rename/recolor a tag once; it updates everywhere.
- Delete a tag; junction rows cascade away, tasks are untouched.
- The fixed palette eliminates arbitrary-color support complexity and keeps chips visually consistent.
- The curated-library model prevents tag proliferation.

**Negative:**
- Two new tables and joins on every task list query (negligible at household scale).
- Users who want inline tag creation during task entry have extra friction — they must go to Settings first. This is intentional for now and can be revisited if real use shows it's a problem.

## Alternatives considered

**JSON array on `tasks.tags`** — rejected. The existing placeholder column stored a raw string. This approach can't support per-tag editable properties (color, rename) that propagate across all uses without a full-table migration.

**Tag groups / categories** — deferred. Not needed until the library grows large enough to warrant hierarchy.

**Inline creation in task forms** — deferred. Keeps the library curated. The picker guides users to Settings with an explicit link when no tags exist.

**Arbitrary colors (hex picker)** — rejected. A fixed palette is simpler to implement, keeps chips visually cohesive, and avoids accessibility surprises with user-chosen color combos.
